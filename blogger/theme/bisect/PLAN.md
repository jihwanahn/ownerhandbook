# JHL-4 — 위젯 렌더 실패 진단·bisect 계획

**증상** (2026-10-16 라이브 재현, `python blogger/theme/verify_applied.py` → **exit 4**)

테마는 적용됐고 SEO 태그도 전부 정상인데, **위젯이 하나도 렌더되지 않습니다.**
섹션 5개가 모두 `<div class='… no-items section' id='…'></div>`로 즉시 닫히고,
페이지에 보이는 텍스트가 `Skip to content`뿐입니다.

**진단 근거 (재현 명령 포함)**

| 관찰 | 값 |
| --- | --- |
| 섹션 5개 | 전부 `no-items`, 위젯 wrapper **0개** |
| Blogger가 클라이언트에 등록한 위젯 | 6개 (`_RegisterWidget` 6줄) |
| 테마가 선언한 위젯 | 8개 (Header1, PageList1, **Label1**, Blog1, HTML1, **Label2**, PageList2, HTML2) |
| 등록조차 안 된 위젯 | **Label1·Label2** — 테마에 있는데 레이아웃에 인스턴스가 없음 |
| 스톡 모바일 템플릿(`?m=1`) | ~~위젯 9개 정상 렌더~~ → **2026-10-17부터 우리 테마가 서빙**(세대 선언이 라이브에 반영됨. 이제 `?m=1`도 빈 페이지) |

즉 Blogger는 위젯 **모델**은 알고 있고(등록 스크립트·설정값까지 계산: `Pages` 위젯에 `Home` 링크,
블로그 이름 등) **마크업만 하나도 만들지 않았습니다.** 위젯 데이터를 등록하는데 그 위젯의
`<div>`와 내용이 없는 상태 = 테마가 컴파일은 됐지만 위젯이 **인스턴스화되지 않은** 상태입니다.

추가로 이 블로그는 **데스크톱만 커스텀 테마**이고 모바일 슬롯은 스톡(구 Basic) 템플릿입니다
(`?m=1`이 Blogger 기본 navbar/crosscol 템플릿으로 렌더). 모바일 우선 요구사항 위반이라
`b:responsive='true'` 선언으로 함께 해결합니다(아래 2단계).

---

## 순서 (한 번에 하나씩, 각 단계 후 `verify_applied.py` 재실행)

각 단계는 대표님 작업 1~3분입니다. **1단계는 붙여넣기 없이 1분**이라 먼저 합니다.

> **2026-10-17 갱신 — 순서가 바뀌었고, 예전 2단계는 사라졌습니다.**
> 라이브 재검증(`verify_applied.py`, 새 검사 `[1b]`·`[6]`) 결과 **현재 파일(=세대 선언 3개
> 포함)이 이미 그대로 서빙 중**입니다(서빙된 `<html>`에 `class='v2'`, `?m=1`도 우리 테마).
> 그래서 **같은 파일을 다시 붙여넣는 것은 아무것도 바꾸지 않습니다** — 2단계(재적용)는
> 아래 "파일이 라이브가 아닐 때"로 내려갔습니다.
> 또한 세대 선언이 위젯 렌더 실패의 원인이 아니라는 것이 실측으로 확인됐습니다(선언이
> 있는 지금도 섹션 5개가 그대로 비어 있음). 대표님 부담을 줄이려면 **1단계 → 1.5단계 →
> 3단계(B0)** 로 가는 것이 맞습니다.
>
> **다음 지시: 1단계(정렬 저장) → 1.5단계(내장 테마 왕복) → 3단계(B0).**
> 새 순서는 `verify_applied.py`의 exit 4 안내 문구에도 반영했습니다.
>
> **2026-10-17 2차 갱신 — 참모장 지시로 2단계가 '선언 세대 현대화'로 바뀌었습니다.**
> 라이브 등록 스크립트를 파싱한 새 증거(위젯 7개 등록·Label1/2 미인스턴스화·섹션 5개 빈 상태)에
> 따라, 1.5단계 뒤 **`owners-handbook-v2-decl.xml` 적용**이 본선입니다(B0보다 먼저 — 대표님 부담이
> 같고 변수는 선언 하나뿐). 파일은 `decl_variant.py`가 v1에서 파생하며, 선언 외 변경이 없음을
> 테스트가 강제합니다(`RESULTS.md` §9). B0/bisect 경로는 이 가설이 틀렸을 때의 다음 순번입니다.

### 1단계 — 레이아웃 정렬 저장 (1분, 붙여넣기 없음)

테마 → **레이아웃** → (확인할 것 2가지) →
① 위젯 상자가 보이는지: `Header / Pages / Categories / Posts / About this site / Browse by category / Pages / HTML`
② **정렬 저장** 버튼 클릭.

- 관찰①에서 **Label(Categories) 상자가 없으면** → 레이아웃에 인스턴스가 아예 안 만들어졌다는 뜻(위 표의 Label1·Label2 누락과 일치) → **1.5단계로**.
- 저장 후 `verify_applied.py` 재실행 → exit 0이면 종료.
- **대표님 회신(2026-10-16, JHL-1 `e028d7c3`): 가젯 상자가 아예 없었습니다.** 즉 레이아웃에
  위젯 인스턴스가 없는 상태가 실측으로 확인됐습니다. 다만 그 회신은 **세대 선언이 서빙되기
  전/직후**의 관찰일 수 있으므로, 저장 후 화면을 한 번 더 확인하는 것이 이 단계의 핵심입니다
  (지금 라이브는 세대 선언이 들어간 상태입니다).

### 1.5단계 — 내장 테마 한 번 왕복 (진단 + 레이아웃 재구성, 붙여넣기 없음, 약 1분)

위젯 렌더가 안 되는 상태에서 **블로그(레이아웃) 쪽 문제인지 테마 파일 쪽 문제인지**를
가르는 가장 싼 실험이고, 동시에 Blogger가 레이아웃을 다시 만드는 **정식 경로**를 태웁니다.

1. 테마 → **맞춤설정 옆 ⋯** → 내장 테마 중 하나(**Contempo** 등) 선택 → 저장
2. 블로그를 열어 **위젯이 보이는지** 확인 (내장 테마에서는 정상적으로 보여야 합니다)
   - **안 보이면** → 이 블로그의 레이아웃 자체가 깨진 상태입니다. 테마 파일 문제가 아니므로
     Blogger 지원 경로로 넘깁니다(파일은 그대로 두고 문의).
3. 다시 **우리 테마로 복귀** — 1단계 백업/복원 업로드 재시도(정식 경로이므로 레이아웃이
   함께 재구성됩니다. 세대 선언이 들어간 지금 파일이라 이전 '복원 거부'가 풀릴 수 있습니다),
   거부되면 2-대안(HTML 편집 붙여넣기)으로 복귀
4. `verify_applied.py` 재실행 → **exit 0이면 종료** (레이아웃 재구성이 원인이었다는 뜻)

글 0건 상태라 독자에게 보이는 변화는 없고, 되돌리기 백업은 그대로 유효합니다.

### 2단계 — 선언 세대 현대화 파일 적용 (`owners-handbook-v2-decl.xml`, 약 3분)

2026-10-17 참모장 지시로 본선이 된 단계입니다. v1과 **선언 메타데이터만** 다른 파일
(`decl_variant.py`가 파생) — CSS·includable·데이터 태그·광고 자리·위젯 설정은 바이트 단위로 동일합니다.
방법은 지금까지와 같습니다: 백업/복원 → 업로드(거부 시 2-대안 HTML 편집 붙여넣기), 또는
**v1이 이미 라이브인 경우**(`[1b]` PASS) 같은 붙여넣기 경로로 이 파일만 교체.

적용 후 `verify_applied.py` 재실행 → exit 0이면 종료, 여전히 4면 3단계(B0)로.

### 2-보조 — (파일이 라이브가 아닐 때만) 현재 파일 재적용

`verify_applied.py`의 **`[1b]` 검사가 "older generation"이라고 할 때만** 하십시오.
2026-10-17 기준으로는 **이미 현재 파일이 서빙 중이라 불필요합니다**(같은 파일을 다시 올려도
결과가 같습니다). 절차는 이전과 동일합니다(2-대안: HTML 편집 → Ctrl+A → Delete → 파일 전체
붙여넣기 → 저장).

`blogger/theme/owners-handbook-v1.xml`을 이전과 **같은 방법**(2-대안: HTML 편집 → Ctrl+A → Delete →
파일 전체 붙여넣기 → 저장)으로 다시 올립니다. 이번 파일에서 바뀐 것은 `<html>` 한 줄입니다:

```
b:version='2' b:responsive='true' class='v2'   ← 3개 선언 추가
```

**이 선언이 왜 들어갔고, 무엇을 고쳤는지(2026-10-17 실측으로 정정):**

- ~~위젯이 렌더되지 않던 문제의 조치~~ → **아닙니다.** 선언이 라이브에 반영된 뒤에도 섹션 5개가
  그대로 비어 있습니다(선언 전/후 모두 `verify_applied.py` exit 4). 위젯 렌더 실패의 원인은
  이 선언이 아니었습니다. 덧붙여, 대표님의 다른 블로그(스톡 테마, 위젯 정상 렌더)는 서빙된
  `<html>`에 **`class='v2'`가 아예 없습니다** — 이 토큰이 위젯 렌더 조건이라는 근거도 없습니다.
- **모바일 슬롯 문제는 실제로 고쳤습니다(유지).** 이 선언 전에는 `?m=1`이 Blogger 스톡 모바일
  템플릿(다른 섹션 구성 + 한국어 UI 문자열)으로 서빙되어 **모바일 우선 요구사항 위반**이었고,
  지금은 `?m=1`도 우리 테마입니다. `verify_applied.py`의 `[6]` 검사가 이 상태를 지킵니다.
- 재적용 절차 자체는 `[1b]` 검사가 "older generation"일 때만 유효합니다(현재는 불필요).

### 3단계 — B0 기준 테마 (진단, 약 3분)

`blogger/theme/bisect/B0-baseline.xml` 붙여넣기. 변수를 최소로 줄인 테마입니다(디자인 아님,
CSS·JSON-LD·광고 없음, 섹션 3·위젯 3, 데이터 태그는 제목 하나뿐).

- **`B0-MARKER-WIDGET-RENDERED`가 보이면** → 이 블로그는 위젯을 정상 렌더합니다. 문제는 우리
  테마 구조 안 → 4단계.
- **아무것도 안 보이면** (Blog 위젯 자체 마크업도 안 보이면) → **이 블로그의 레이아웃 쪽 문제**가
  유력합니다(1.5단계에서 내장 테마도 비어 있었다면 더 확실). 테마 파일 문제가 아니므로 5단계.
  참고: 같은 증상의 공개 사례(support.google.com/blogger/thread/463778303)에서는 **같은 블로그·
  같은 붙여넣기 경로에서 최소 버전 테마는 위젯이 정상 렌더**됐습니다 — 즉 "손으로 붙여넣으면
  위젯이 안 나온다"는 일반 규칙은 아닙니다. 그 사례는 위젯 `version` 1/2, id 충돌, dangling
  `b:include`를 모두 배제한 뒤 최소 테마부터 하나씩 되돌리는 방식으로 좁혔습니다.

### 4단계 — 테마 내부 bisect (B0가 성공한 경우에만)

한 번에 하나씩 변수를 제거하며 같은 방식으로 붙여넣기 (각 3분):

1. B0 + CSS(`b:skin`) 복원 → 실패 시 CSS 무관
2. B0 + 섹션 5개/위젯 8개 복원 (includable은 단순 유지) → 실패 시 위젯 개수·종류(Label/PageList) 의심
3. B0 + 우리 includable(main/post/nextprev/comments) 복원 → 실패 시 includable 내부 로직
4. B0 + JSON-LD/OG/head 블록 복원 → 실패 시 head 영역 상호작용

제가 각 단계 파일을 만들어 드립니다(요청만 주시면 바로).

### 5단계 — 블로그/경로 문제로 넘김 (B0도 실패한 경우)

- **정식 설치 경로 재시도**: 백업/복원 → 업로드(이전엔 '복원 거부'였음) → 실패 시 그 문구 그대로.
- Blogger의 **테마 검증기**가 붙여넣기 경로에서 위젯을 재인스턴스화하지 않는 케이스이므로,
  공개 사례(thread/463778303 — "minimal 2-widget theme works / fuller fails")와 대조해
  참모장·대표님 판단으로 지원 경로를 검토합니다.
- 이 경우에도 테마 파일 자체는 오프라인 42개 검사 + 47개 테스트를 통과한 상태입니다.

**되돌리기**: 각 단계 전 테마 → ⋮ → 백업/복원 → 백업으로 현재 테마를 받아두시고, 되돌릴 때 그
파일을 업로드하거나 2단계 방식으로 다시 붙여넣으면 됩니다. B0를 올린 뒤 원래 테마로 돌아오려면
`owners-handbook-v1.xml`을 다시 붙여넣으면 됩니다(2단계와 동일).

## 판정 기준 (JHL-4 수용 조건에 추가)

`verify_applied.py`에 **위젯 렌더 검사**를 넣었습니다(`[5]`, exit code **4**). 이제 JHL-4 판정은
"마커·SEO 통과"가 아니라 **"섹션에 위젯 wrapper가 실제로 존재"**까지 봐야 통과입니다.
검사는 테마 파일이 선언한 위젯 8개 각각에 대해 `RENDERED / REGISTERED BUT EMPTY /
NOT INSTANTIATED`를 출력하므로, 위 실패가 다시 조용히 통과할 수 없습니다.
